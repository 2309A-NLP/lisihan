# PDF招股说明书智能问答系统技术文档

工单编号：人工智能NLP-RAG-基于PDF文档的问答系统

## 1. 项目概述

本项目面向招股说明书 PDF 文档构建智能问答系统，重点处理以下场景：

- 招股说明书正文问答
- 财务、股东、发行概况等表格内容解析
- 章节化长文档分块
- 固定元数据问题直答，如法定代表人、注册资本、成立日期、注册地址
- BM25 + Milvus 向量检索 + RRF 融合
- Redis 保存最近 20 条短期对话
- Milvus 保存长期优质问答记忆

系统入口：

- `main.py`：统一启动入口，支持 Web 模式和 CLI 模式
- `app.py`：Streamlit 前端页面
- `pdf_parser/`：PDF 解析与分块模块
- `src/rag_engine.py`：RAG 主流程编排

## 2. 当前架构

系统整体流程如下：

1. 读取 `data/` 目录中的 PDF 文件
2. 使用 PyMuPDF 提取正文文本块
3. 使用 pdfplumber 提取表格块
4. 合并文本块和表格块，并按页码、Y 坐标排序
5. 合并被 PyMuPDF 错切的相邻文本块
6. 对长文本按段落和句子继续切分
7. 提取文档固定元数据
8. 构建 BM25 索引
9. 对普通语义问题使用 Milvus 向量检索辅助召回
10. 使用 RRF 对 BM25 和向量检索结果融合排序
11. 对精确问题使用快速路径跳过向量检索
12. 使用规则抽取、元数据直答或 LLM 生成答案
13. 使用 Redis 保存短期对话，使用 Milvus 保存长期优质问答

## 4. 核心模块

### 4.1 PDF 解析模块

位置：`pdf_parser/`

当前解析流程：

- `text_extractor.py` 使用 `page.get_text("dict")` 获取 PyMuPDF 文本结构
- `table_extractor.py` 使用 pdfplumber 提取表格
- `chunk_merger.py` 合并文本和表格，并处理 PyMuPDF 错切问题
- `metadata_extractor.py` 从招股说明书前若干页抽取固定字段

解析输出包含：

- `source_file`
- `source_path`
- `page_count`
- `chunk_count`
- `table_count`
- `document_metadata`
- `chunks`

同时会生成：

```text
parsed_pdfs/招股说明书1_chunks.json
parsed_pdfs/招股说明书1_metadata.json
```

### 4.2 文档元数据抽取

位置：`pdf_parser/metadata_extractor.py`

用于解决唯一固定字段问题，避免依赖检索和 LLM 猜测。

当前抽取字段：

```python
{
    "company_name": "武汉兴图新科电子股份有限公司",
    "legal_representative": "程家明",
    "registered_capital": "5,520万元",
    "establishment_date": "2004年6月17日",
    "registered_address": "湖北省武汉东湖新技术开发区关山大道1号软件产业三期A3栋8层"
}
```

RAG 回答时会优先使用元数据回答以下问题：

- 法定代表人是谁
- 注册资本是多少
- 公司成立日期是什么
- 注册地址在哪里
- 公司名称是什么

### 4.3 检索模块

位置：`src/retriever.py`

当前检索策略：

- BM25：主召回方式，适合招股说明书中的精确关键词问题
- Milvus：向量检索，用于普通语义问题辅助召回
- RRF：融合 BM25 和向量召回结果
- 快速路径：对精确问题跳过向量检索，降低响应时间

ChromaDB 已移除，项目不再依赖 `chromadb` 或 `chroma_db` 文件夹。

精确问题快速路径包括：

- 法定代表人
- 注册资本
- 技术标准
- 上游/下游
- 重要供应商
- 军用领域收入
- 收入占比/比重
- 募集资金

### 4.4 Query 改写

位置：`src/rag_engine.py`

用于将用户自然表达映射到招股书标准字段。

示例：

```text
用户问题：
报告期内，武汉兴图新科电子股份有限公司来自军用领域的收入分别是多少？

改写后：
直接和间接向国防客户的销售额合计分别是多少
```

这样可以避免系统把“直接军方收入”和“间接军方收入”分开回答。

### 4.5 问题分类

位置：`utils/question_classifier.py`

问题类型：

- `numeric`：金额、数量、注册资本等
- `percentage`：占比、比重、比例、百分比
- `entity`：实体、机构、人员、领域、标准等

分类结果会影响：

- 是否跳过长期记忆
- 是否走精确检索
- 使用哪个 Prompt
- 是否启用本地规则抽取

### 4.6 回答生成与后处理

位置：`utils/llm_engine.py`

回答优先级：

1. 文档元数据直答
2. 长期记忆命中
3. 检索上下文规则抽取
4. LLM 生成
5. 离线兜底抽取

后处理负责：

- 清除表格竖线和残片
- 过滤银行、授信、合同等无关上下文
- 固定法定代表人输出为姓名
- 固定注册资本输出为金额
- 军用领域收入输出合计值
- 比重问题限制输出百分比

### 4.7 记忆模块

位置：`src/memory_manager.py`

短期记忆：

- 使用 Redis
- 保存最近 20 条用户和助手消息
- 默认 TTL 来自 `Config.REDIS_SESSION_TTL`

长期记忆：

- 使用 Milvus
- 用户点击“有帮助”后，将优质问答写入长期记忆
- RAG 在非精确问题上会尝试搜索长期记忆

精确问题会跳过长期记忆，避免首次加载 embedding 模型导致响应变慢。


常见问题：

- Milvus 不可用：检查 `localhost:19530` 是否监听，确认 `pymilvus` 已安装

## MinerU parsing workflow

The default PDF parser backend is MinerU. Core defaults are:

```python
PDF_PARSER_BACKEND = "mineru"
PDF_PARSE_OUTPUT_DIR = "./mineru_output"
MINERU_OUTPUT_DIR = "./mineru_output"
MINERU_BACKEND = "pipeline"
MINERU_METHOD = "txt"
MINERU_MODEL_SOURCE = "modelscope"
MINERU_DEVICE_MODE = "cpu"
MINERU_CUDA_VISIBLE_DEVICES = ""
```

MinerU raw files and project-adapted chunk JSON are stored under `mineru_output`.
Expected raw output layout:

```text
mineru_output/招股说明书1/auto/招股说明书1.md
mineru_output/招股说明书1/auto/招股说明书1_content_list.json
mineru_output/招股说明书2/auto/招股说明书2.md
mineru_output/招股说明书2/auto/招股说明书2_content_list.json
```

The project adapter writes RAG-ready files:

```text
mineru_output/招股说明书1_chunks.json
mineru_output/招股说明书2_chunks.json
```

`*.md` and `*_content_list.json` are required. If either file is missing, parsing fails with an explicit MinerU/WSL error instead of silently falling back to the local parser. The adapted JSON keeps the original `chunks` contract and records `parser_backend`, `mineru_markdown`, and `mineru_content_list`.

Batch parsing:

```powershell
.\.venv\Scripts\python.exe run_mineru_wsl.py data --output-dir mineru_output
.\.venv\Scripts\python.exe run_mineru_wsl.py data\招股说明书1.pdf data\招股说明书2.pdf --output-dir mineru_output
```

The WSL runner uses `wslpath` for Windows-to-WSL path conversion, reads output as UTF-8, initializes Conda PATH safely, and includes WSL/MinerU stdout and stderr in failures.

### MinerU CLI method compatibility

For current MinerU CLI versions, `-m/--method` accepts only `auto`, `txt`, or `ocr`. The project keeps `MINERU_BACKEND="pipeline"` as the strategy label and uses ModelScope by default, but the command sent to MinerU is `-m auto` through `MINERU_METHOD="auto"`. If an old environment variable still sets `MINERU_BACKEND=pipeline`, the WSL runner maps it to `auto` before execution.
