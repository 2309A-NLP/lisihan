## 2. 检索层优化

### 2.1 混合检索（BM25 + 向量 + RRF）

**问题背景：** 招股说明书问题分为两类——精确关键词问题（法定代表人、注册资本）和语义问题（关联方关系、业务描述）。单一检索方式无法兼顾。

**优化方案：** 实现了 BM25 全文检索 + Milvus 向量检索 + RRF 融合的三层检索架构。

| 组件 | 作用 | 配置参数 |
|------|------|---------|
| BM25 | 关键词精确匹配，适合专有名词/数值 | `BM25_K=6`, `BM25_RRF_WEIGHT=3.0` |
| Milvus 向量 | 语义近似匹配，适合抽象概念 | `VECTOR_K=4`, `VECTOR_RRF_WEIGHT=1.0` |
| RRF 融合 | 倒序排名融合，合并两种召回结果 | `RRF_K=30`, `FINAL_K=3` |

**代码位置：** `retriever/hybrid.py` → `search()` 方法；`retriever/fusion.py` → `_rrf_fuse()`

**效果：** 精确问题 BM25 主导，语义问题向量补充，RRF 融合综合排序。BM25 权重（3.0）高于向量（1.0），反映招股书以关键词匹配为主的特点。

**备选融合方式：** 也支持加权平均融合 `weighted_average`，Web 界面可切换。

### 2.2 动态权重策略

**问题背景：** 不同问题类型对 BM25 和向量检索的依赖程度不同。专有名词问题应偏 BM25，抽象语义问题应偏向量。

**优化方案：** 根据问题内容动态分配 BM25 / 向量权重：

| 问题类型 | 触发条件 | BM25:向量权重 |
|---------|---------|---------------|
| `proper_noun` | 匹配到公司名、人名、标准名 | 0.80 : 0.20 |
| `numeric` | 包含"多少""金额""比重"等 | 0.70 : 0.30 |
| `abstract` | 字数 > 20 且含"什么" | 0.40 : 0.60 |
| `default` | 其他 | 0.65 : 0.35 |

**代码位置：** `retriever/hybrid.py` → `get_dynamic_weights()`

**效果：** 问"法定代表人是谁"时 BM25 占 80%，问"公司的业务特点是什么"时向量占 60%。

### 2.3 同义词扩展查询

**问题背景：** 招股书原文用"直接和间接向国防客户的销售额合计"，用户问"军用领域收入"，BM25 因词不匹配导致召回差。

**优化方案：** 预定义同义词映射表，BM25 检索前对查询进行同义词扩展：

```python
_query_synonyms = {
    "军用领域收入": ["直接和间接向国防客户的销售额合计", "销售额合计"],
    "收入": ["营业收入", "主营业务收入", "销售收入"],
    "技术标准": ["参与制定", "某视频技术规范1.0"],
    "重要供应商": ["国防军队视频指挥领域", "视频指挥领域"],
    # ... 共约 20 组
}
```

**代码位置：** `retriever/hybrid.py` → `_expand_query()`（调用了同义词映射）

**效果：** 用户口语化表述映射到招股书标准措辞，BM25 召回率大幅提升。

### 2.4 精确查询快速路径

**问题背景：** 向量检索需要加载 sentence-transformer 模型（约 1-2 秒首次加载），对于法定代表人、注册资本等精确问题，向量检索无增益。

**优化方案：** 在 `_is_exact_query()` 判断问题是否为精确查询，如是则跳过向量检索，仅使用 BM25。

```python
if SKIP_VECTOR_FOR_EXACT_QUERIES and self._is_exact_query(query):
    return [(hit.doc, hit.score) for hit in bm25_hits[:final_top_k]]
```

**代码位置：** `retriever/hybrid.py` → `search()` 第 376 行

**效果：** 精确问题响应时间从 ~2s 降到 ~0.3s。

### 2.5 自动模糊降级

**问题背景：** 用户输入或 OCR 误差可能导致精确短语匹配无结果。

**优化方案：** 当 BM25 精确/布尔匹配结果 < 2 条时，自动降级到模糊匹配（SequenceMatcher 相似度 ≥ 0.72），并标记 `auto_fallback=True`。

**代码位置：** `retriever/hybrid.py` → `_bm25_search()` 第 166 行

**效果：** 对模糊问题仍能召回结果，避免"找不到答案"。Web 界面自动展示"已使用模糊匹配"提示。

### 2.6 检索结果缓存

**优化方案：** 使用 `OrderedDict` 实现 LRU 搜索缓存，容量 100 条。相同 query + mode + 权重组合命中时直接返回。

**代码位置：** `retriever/cache.py` → `SearchCacheMixin`

## 3. 回答质量优化

### 3.1 元数据直答

**问题背景：** 法定代表人、注册资本、成立日期等固定字段，每次都要检索 + LLM 生成，耗时且易出错。

**优化方案：** PDF 解析时从正文首页提取元数据（正则匹配），问答时优先检查元数据命中。

**支持字段：**

| 元数据字段 | 示例值 | 触发问题 |
|-----------|--------|---------|
| `company_name` | 武汉兴图新科电子股份有限公司 | "公司名称是什么" |
| `legal_representative` | 程家明 | "法定代表人是谁" |
| `registered_capital` | 5,520万元 | "注册资本是多少" |
| `establishment_date` | 2004年6月17日 | "公司成立日期" |
| `registered_address` | 湖北省武汉... | "注册地址在哪里" |

**代码位置：** `pdf_parser/metadata_extractor.py` + `rag_engine/answering.py` → 回答优先级路径

**效果：** 零秒响应，100% 准确率。完全避免检索偏移和 LLM 幻觉。

### 3.2 本地规则抽取

**问题背景：** 对数值、百分比、实体类问题，LLM 调用耗时且可能生成错误格式。

**优化方案：** 优先使用正则和规则从检索片段中直接抽取答案：

- 数值问题：`\d{1,3}(?:,\d{3})*(?:\.\d+)?\s*(?:万元|元|%)`
- 百分比问题：`\d+(?:\.\d+)?\s*%`
- 实体问题：上下文定位后截取
- 表格问题：按行解析 Markdown 表格

**代码位置：** `utils/llm_engine/local_answer.py` → `_extract_answer_from_context()`, `_extract_complete_entity_answer()`

**效果：** 对数值/实体类问题，响应时间从 ~1.5s 降到 ~0.1s，格式一致性 100%。

### 3.3 质量校验与重试

**问题背景：** 检索结果不佳时 LLM 生成的答案可能空泛或错误，需要二次校验。

**优化方案：** 回答生成后调用 `validate_answer_quality()` 进行多维质量校验：

| 校验维度 | 检测内容 | 扣分幅度 |
|---------|---------|---------|
| 空答案 | answer 为空或 "没有找到相关信息" | confidence → 0.0 |
| 过短答案 | < 2 字符 | -0.45 |
| 百分比缺失 | 问题含"占比"但回答无百分比 | -0.55 |
| 数字缺失 | 数值问题无数字 | -0.45 |
| 公司实体缺失 | 问题提到公司但回答未涉及 | -0.25 |
| 关联方/收入混淆 | "关联方" 问题回答含收入数据 | -0.65 |

**校验未通过时：** 自动执行质量重试——用 BM25 模式重新检索并生成答案，替换低质量结果。

**时间预算：** `QUALITY_RETRY_MAX_ELAPSED_SECONDS=2.2`，超时则放弃重试，保证总响应 < 3s。

**代码位置：** `validation/answer_validator.py`, `rag_engine/answering.py` → `_retry_answer_for_quality()`

### 3.4 负向问题处理

**问题背景：** "哪些关联方不存在控制关系""未披露的关联方有哪些"等否定类问题，LLM 容易混淆肯定/否定。

**优化方案：** 两步法：

1. 先检索"存在控制关系的关联方"得到正面列表
2. 再从全量关联方中排除正面列表，得到否定答案

支持 `除了...之外` 排除语法，以及"未披露"关键词检测。

**代码位置：** `validation/negative_handler.py` → `handle_negative_query()`

### 3.5 答案后处理

**优化方案：** `postprocess_answer()` 对 LLM 原始输出进行多项修正：

- 删除表格竖线和排版残片
- 过滤银行/授信/合同等无关上下文
- 固定法定代表人输出为纯姓名（去掉职务）
- 固定注册资本输出为货币格式
- 军用领域收入输出合计值
- 比重问题限制仅输出百分比

**代码位置：** `utils/llm_engine/` → `postprocess_answer()`

### 3.6 长期记忆复用

**优化方案：** 用户点击"有帮助"后将优质问答存入长期记忆。下次遇到语义相似问题（embedding 相似度 ≥ 0.8）时优先返回记忆中的答案。

**精确问题跳过逻辑：** 避免首次加载 embedding 模型拖慢响应。

**代码位置：** `memory_manager.py`, `rag_engine/answering.py` → `_answer_from_long_term_memory()`

## 4. 性能优化

### 4.1 回答缓存

**问题背景：** 用户在对话中可能重复提问相同或相似问题。

**优化方案：** 进程内字典缓存，缓存键包含 `question + retrieval_mode + retrieval_config + session_id`，TTL 默认 30 秒。

```python
_answer_cache: Dict[str, Tuple[RAGResponse, float]]  # (response, timestamp)
ENABLE_ANSWER_CACHE = true
ANSWER_CACHE_TTL_SECONDS = 30
```

**代码位置：** `rag_engine/cache.py` → `AnswerCacheMixin`

**效果：** 30 秒内重复问题直接命中缓存，零检索零计算。

### 4.2 Milvus 自动降级

**问题背景：** Milvus 服务可能因 Docker 未启动或网络问题不可用。

**优化方案：** 首次 Milvus 连接失败时将 `"milvus"` 加入 `_disabled_vector_backends` 集合，后续请求直接跳过向量检索，仅使用 BM25。

**代码位置：** `retriever/vector.py` → `_milvus_search()` 第 90 行

**效果：** Milvus 故障时系统不崩溃，功能降级为纯 BM25 模式。

### 4.3 上下文截断

**问题背景：** 检索返回的文档片段长度不定，LLM 上下文窗口浪费。

**优化方案：** `_trim_context_part()` 按 TOP_K 动态平分 `LLM_CONTEXT_MAX_CHARS`，每个片段截断到 `max_chars / TOP_K`。

**代码位置：** `rag_engine/context.py` → `_trim_context_part()`

### 4.4 搜索缓存 LRU

**优化方案：** `OrderedDict` 实现 LRU，容量 100 条。每次命中后移到最后，容量满时淘汰最早条目。

**代码位置：** `retriever/cache.py`

### 4.5 多模态 Redis 缓存

**优化方案：** 图片问答结果写入 Redis，TTL 默认 1 小时。缓存键为 `image_path + question` 的 SHA256 哈希。

**代码位置：** `rag_engine/multimodal.py` → `_multimodal_cache_key()`

### 4.6 时间预算控制

**问题背景：** 质量重试可能导致整体响应时间失控。

**优化方案：** `QUALITY_RETRY_MAX_ELAPSED_SECONDS=2.2`，如果质量重试时已超过该时间预算，跳过重试直接返回初始答案。

**代码位置：** `rag_engine/answering.py` → `_retry_answer_for_quality()` 第 86 行

## 5. 多轮对话优化

### 5.1 指代消解

**问题背景：** 用户连续问"武汉力源信息技术股份有限公司的法定代表人是谁""注册资本是多少"，第二问省略了公司名。

**优化方案：** 基于规则的 `CoreferenceResolver`：

- 维护公司别名表（"武汉力源" → "武汉力源信息技术股份有限公司"）
- 识别代词："这个公司"、"该公司"、"他"
- 识别切换话题："那兴图新科呢？"→ 切换公司实体
- 将省略问题补全为完整问题后再检索

```python
COMPANY_ALIASES = {
    "武汉兴图新科电子股份有限公司": ("武汉兴图新科", "兴图新科", ...),
    "武汉力源信息技术股份有限公司": ("武汉力源", "力源信息", ...),
}
```

**代码位置：** `coreference_resolver.py`

### 5.2 Session 管理

**优化方案：** `SessionManager` 保存最近 N 轮问答（默认 5 轮），记录 `question → resolved_question → answer → mentioned_companies` 的完整链路。

历史仅作为指代消解参考，答案仍由 RAG 检索生成。

**代码位置：** `session_manager.py`

### 5.3 Redis / 进程内存双模式

**优化方案：** Redis 可用时使用 Redis（TTL 86400s），Redis 不可用时自动降级到进程内 `deque(maxlen=5)`。

**代码位置：** `session_manager.py` → `is_available()`

## 6. Query 理解优化

### 6.1 Query 改写

**问题背景：** 用户问"军用领域的收入是多少"，招股书原文写"直接和间接向国防客户的销售额合计"，BM25 难以匹配。

**优化方案：** `rewrite_query()` 将业务口径问题改写为招股书标准字段：

| 用户问题 | 改写后 |
|---------|-------|
| 军用领域的收入是多少 | 直接和间接向国防客户的销售额合计分别是多少 |
| 募集资金拟投资哪些项目 | 本次募集资金拟投资以下项目 项目名称 计划总投资 |
| xx募集资金用于什么 | 募集资金 金额 + 补充流动资金 项目名称 |

**改写失败回退：** 改写后的查询如无检索结果，自动用原问题重试。

**代码位置：** `processing/query_rewriter.py`, `rag_engine/context.py` → `_build_context()` 第 87-99 行

### 6.2 问题分类

**优化方案：** `QuestionClassifier` 将问题分为 `numeric` / `percentage` / `entity` / `general`，分类结果影响：

- 是否走快速路径
- 使用哪个 Prompt 模板
- 是否启用本地规则抽取
- 是否跳过长期记忆

**代码位置：** `utils/question_classifier.py`

### 6.3 文档自动路由

**优化方案：** 根据问题中出现的公司名自动路由到对应 PDF：

| 问题含有关键词 | 路由到 |
|---------------|-------|
| 武汉力源 / 力源信息 | 招股说明书2.pdf |
| 武汉兴图 / 兴图新科 | 招股说明书1.pdf |

**代码位置：** `processing/query_rewriter.py` → `select_pdf()`, `_infer_source_file_from_question()`

## 7. 多模态优化

### 7.1 语义识别触发

**问题背景：** 用户问组织结构图、IC 市场增长图等问题，需要调用多模态视觉模型。

**优化方案：** 通过关键词 + 语义组合判断：

```python
image_keywords = ["组织结构图", "增长图", "图中", "IC市场", "销售部构成"]
looks_like_image_question = any(keyword in q for keyword in image_keywords) or asks_structure_or_count
```

**代码位置：** `rag_engine/multimodal.py` → `_is_multimodal_work_order_question()`

### 7.2 图片智能定位

**优化方案：** 多级定位策略：

1. **配置表直定位：** `MULTIMODAL_WORK_ORDER_IMAGES` 中的固定路径
2. **按页面渲染：** 配置了页码时动态渲染 PDF 页面为图片
3. **关键词搜索定位：** 在 parsed JSON 中按章节标题搜索页码
4. **最大图片选择：** 同页多张图片时按 bbox 面积选最大

**代码位置：** `rag_engine/multimodal.py` → `_select_multimodal_image()`

### 7.3 多级缓存

**优化方案：** 双重缓存：
- **进程内存：** 走通用回答缓存 `_answer_cache`（30s TTL）
- **Redis：** 专用多模态缓存 `ENABLE_MULTIMODAL_REDIS_CACHE`（1h TTL）

**代码位置：** `rag_engine/multimodal.py` → `_get_multimodal_cached_payload()`, `_set_multimodal_cached_payload()`

## 8. PDF 解析优化

### 8.1 MinerU 适配

**优化方案：** MinerU 输出的 markdown + content_list.json 转换为项目统一的 `chunks` 格式。支持 `MINERU_METHOD=auto/txt/ocr` 三种模式。

**代码位置：** `pdf_parser/mineru_backend.py`

### 8.2 分片解析

**问题背景：** 大量页面 PDF 发送到 MinerU 可能超时断开。

**优化方案：** `run_mineru_segmented.py` 将大 PDF 按页数分片（默认 20 页/片），分别解析后合并内容。

**代码位置：** `run_mineru_segmented.py`

### 8.3 WSL 桥接

**优化方案：** WSL 路径自动转换（`wslpath`），Conda 环境自动检测，输出 UTF-8 解码，超时控制。

**代码位置：** `src/utils/wsl_mineru.py`
