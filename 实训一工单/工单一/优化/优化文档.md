## 1. 性能优化

### 1.1 🔴 BM25 索引持久化

| 当前问题 | 优化建议 |
|---------|---------|
| 每次启动系统都要重新解析 PDF、重建 BM25 索引 | 将 BM25 索引序列化到磁盘，启动时直接加载 |

**现状代码**（rag_engine.py 第 83 行）：

```python
documents = self.pdf_parser.parse_multiple_pdfs(Config.PDF_DIR)
self.vector_store.create_vectorstore(documents)
```

每次 `initialize_project_knowledge_base()` 都要解析 PDF，对于 2000+ chunk 的文档耗时约 10~30 秒。

**建议方案**：

```
方案 A（推荐）：pickle 序列化
├── 首次：parse PDF → build BM25 → 序列化到 disk/
├── 后续：检查 disk/ 缓存文件 → 反序列化加载
└── 用户主动点"重建索引"时才重新解析

方案 B：沿用 MinerU 的 Markdown 缓存
├── MINERU_USE_CACHE=1 时跳过重复 PDF 解析
└── 但 BM25 索引本身仍需重建

预期效果：启动时间从 10~30 秒 降低到 <1 秒
```

### 1.2 🟡 语义化分块

| 当前问题 | 优化建议 |
|---------|---------|
| `_chunk_text` 和 `_chunk_markdown_text` 都是基于字符数或空行切割 | 使用语义边界（段落、标题、句子）进行分块 |

**现状代码**（pdf_parser.py 第 71~73 行）：

```python
step = max(1, self.chunk_size - self.chunk_overlap)
start = 0
while start < len(text):
    end = min(len(text), start + self.chunk_size)
```

**建议方案**：

```
├── 优先按 Markdown 标题（## / ###）分块
├── 其次按段落（双换行）分块
├── 再按句子边界分块
└── 最后才用字符数截断

预期效果：减少"一句话被切到两个chunk"的检索丢失问题
```

### 1.3 🟡 减少重复 Tokenize

| 当前问题 | 优化建议 |
|---------|---------|
| `vector_store.py` 和 `llm_engine.py` 各有一套 `_tokenize`、`_extract_keywords` 实现，停用词表重复维护 | 提取公共分词模块，统一调用 |

**现状代码**：

- `vector_store.py` 第 68~80 行：`_tokenize` 方法
- `llm_engine.py` 第 57~93 行：`_extract_keywords` 方法
- `evaluator.py` 第 234~281 行：`_extract_keywords` 方法（第三次定义）

三处各自维护停用词表，增删不一致。

### 1.4 🟢 LLM 调用超时控制

| 当前问题 | 优化建议 |
|---------|---------|
| LLM API 调用没有设置超时，网络波动时可能卡死数分钟 | 为 OpenAI 客户端设置 timeout |

**现状代码**（llm_engine.py 第 43 行）：

```python
return OpenAI(api_key=Config.LLM_API_KEY, base_url=Config.LLM_API_BASE_URL)
```

**建议方案**：

```python
return OpenAI(
    api_key=Config.LLM_API_KEY,
    base_url=Config.LLM_API_BASE_URL,
    timeout=timeout or httpx.Timeout(15.0, connect=5.0),  # 新增超时
)
```

## 2. 代码质量优化

### 2.1 🔴 提取过长方法 `_extract_answer_from_context`

| 当前问题 | 优化建议 |
|---------|---------|
| `_extract_answer_from_context` 长达 100+ 行（第 152~236 行），内含 6 个以上的特定问题分支 | 拆分为策略模式或多 dispatch |

**现状代码**（llm_engine.py 第 152~236 行）：

```python
def _extract_answer_from_context(self, question: str, context: str) -> str:
    # ... 约 84 行代码
    # 包含：参与制定 → 哪个领域 → 国家科技进步一等奖 → 补充流动资金
    #      → 注册资本 → 法定代表人 → 军用/民用收入 → 兜底句子匹配
```

**建议方案**：

```python
# 方案：提取为策略列表
_EXTRACTORS = [
    _extract_technical_standard,
    _extract_supplier_field,
    _extract_engineering_award,
    _extract_supplement_capital,
    _extract_registered_capital,
    _extract_legal_representative,
    _extract_military_revenue,
    _extract_by_sentence_matching,
]

def _extract_answer_from_context(self, question, context):
    for extractor in _EXTRACTORS:
        result = extractor(question, context)
        if result:
            return result
    return ""
```

**好处**：每个提取策略独立可测，新增问题规则时无需修改长函数。

### 2.2 🔴 消除跨模块私有方法调用

| 当前问题 | 优化建议 |
|---------|---------|
| `rag_engine.py` 第 161 行调用了 `llm_engine._extract_answer_from_context`（私有方法）| 改为公开接口或提取公共方法 |

**现状代码**（rag_engine.py 第 160~163 行）：

```python
if question_type in {"numeric", "percentage"}:
    extracted = self.llm_engine._extract_answer_from_context(question, context)
```

**建议方案**：

```python
# 方案 1：提取为公共方法
class LLMEngine:
    def extract_from_context(self, question, context):
        return self._extract_answer_from_context(question, context)

# 方案 2：移到 RAGEngine 中
class RAGEngine:
    def _local_extract(self, question, context):
        # 仅做数字/百分比本地提取
        ...
```

### 2.3 🟡 统一配置管理

| 当前问题 | 优化建议 |
|---------|---------|
| 配置来源分散：`.env`、`config.py`、`config.json` | 统一使用 `.env` + 环境变量，移除 `config.json` |

`config.json` 目前只用于 MinerU，建议合并到 `Config` 类中，减少配置入口数量。

### 2.4 🟡 移除死代码

| 文件 | 死代码 | 说明 |
|------|--------|------|
| `pdf_parser.py` 第 179~181 行 | `extract_tables()` | 方法体只有 `return []`，从未被调用 |
| `rag_engine.py` 第 199~200 行 | `answer()` | 仅转发到 `ask()`，可以移除 |
| `vector_store.py` | `load_vectorstore()` / `delete_collection()` | 逻辑简单或未使用 |
| `rag_engine.py` 第 202~216 行 | `stream_answer()` | 内部调用了 `_build_context` 但从不流式输出 |

### 2.5 🟢 Python 编码规范

| 问题 | 建议 |
|------|------|
| 文件混合 CRLF / LF 换行符 | 统一使用 LF（`\n`） |
| 缺少类型注解（部分函数） | 补充类型注解 |
| `import re` 在函数内部（evaluator.py 第 178、235 行） | 统一移到文件顶部 |
| 部分变量名不够语义化（`q`、`r`、`cr`、`af`） | 改用完整命名 |

## 3. 架构优化

### 3.1 🔴 类名与实际功能不匹配

| 当前类名 | 实际功能 | 建议改名 |
|----------|---------|---------|
| `VectorStore` | 只做 BM25 检索，无向量存储 | `BM25Store` 或 `Retriever` |
| `RAGEngine.ask()` | 返回完整回答 | `RAGEngine.answer()` 已足够 |

### 3.2 🔴 模块间紧耦合

**问题**：`RAGEngine` 直接实例化所有依赖，不利于测试和替换。

```python
class RAGEngine:
    def __init__(self):
        self.pdf_parser = PDFParser()           # 硬编码
        self.vector_store = VectorStore()       # 硬编码
        self.llm_engine = LLMEngine()           # 硬编码
        self.question_classifier = QuestionClassifier()  # 硬编码
```

**建议方案：依赖注入**

```python
class RAGEngine:
    def __init__(
        self,
        pdf_parser: PDFParser = None,
        vector_store: VectorStore = None,
        llm_engine: LLMEngine = None,
        question_classifier: QuestionClassifier = None,
    ):
        self.pdf_parser = pdf_parser or PDFParser()
        self.vector_store = vector_store or VectorStore()
        self.llm_engine = llm_engine or LLMEngine()
        self.question_classifier = question_classifier or QuestionClassifier()
```

**好处**：
- 单元测试可以注入 Mock 对象
- 将来替换为其他检索方式（如向量检索）无需改 RAGEngine
- 显式声明依赖关系

### 3.2 🟡 缺少 API 接口

| 问题 | 建议 |
|------|------|
| 只能通过 Streamlit 或 CLI 调用系统 | 增加 REST API 接口，便于集成到其他系统 |

**建议方案**：

```python
# 新增 api.py
from fastapi import FastAPI
from src.rag_engine import RAGEngine

app = FastAPI()
engine = RAGEngine()

@app.post("/api/ask")
async def ask(question: str, top_k: int = 4):
    response = engine.ask(question)
    return {
        "answer": response.answer,
        "contexts": response.retrieved_contexts,
        "time": response.total_time,
    }

@app.post("/api/reindex")
async def reindex():
    result = engine.initialize_project_knowledge_base()
    return {"success": result.success, "documents": result.document_count}
```

### 3.3 🟡 无关配置分离

`Config` 类混合了以下不相关配置：

```
检索相关    → TOP_K_RETRIEVAL, BM25_TOP_K, COLLECTION_NAME
LLM 相关    → LLM_MODEL, LLM_API_KEY, LLM_API_BASE_URL
PDF 解析相关 → PDF_PARSER_BACKEND, MINERU_*
评测相关    → TASK_ID, EVALUATION_QUESTIONS
```

**建议**：拆分为 `RetrievalConfig`, `LLMConfig`, `PDFParserConfig`, `EvalConfig` 等。

### 3.4 🟢 添加单元测试

**建议覆盖**：

| 模块 | 关键测试 |
|------|---------|
| `question_classifier.py` | 10 道硬编码规则是否匹配正确 |
| `vector_store.py` | BM25 检索结果排序是否正确 |
| `evaluator.py` | 严格匹配逻辑是否准确 |
| `llm_engine.py` | 离线提取是否返回预期内容 |

## 4. 用户体验优化

### 4.1 🔴 真正的流式输出

| 当前问题 | 优化建议 |
|---------|---------|
| app.py 第 141~144 行是模拟流式（每 18 个字符 + time.sleep）| 使用 LLM 的真实 SSE 流式响应 |

**现状代码**（app.py 第 141~144 行）：

```python
for i in range(0, len(response.answer), 18):
    content += response.answer[i : i + 18]
    placeholder.markdown(content)
    time.sleep(0.01)
```

**建议方案**：

```python
# rag_engine.py
def ask_stream(self, question: str):
    question_info = ...
    context = self._build_context(question)
    for chunk in self.llm_engine.stream_answer_stream(question, context):
        yield chunk

# llm_engine.py
def stream_answer_stream(self, question, context):
    response = self.client.chat.completions.create(
        model=...,
        messages=...,
        stream=True,  # 开启真实流式
    )
    for chunk in response:
        if chunk.choices[0].delta.content:
            yield chunk.choices[0].delta.content
```

### 4.2 🟡 检索过程状态反馈

**问题**：用户提问后页面空白等待，没有"正在检索…"的提示。

**建议**：检索时显示状态，使用 Streamlit 的 `with st.status("正在检索...")` 或 `st.spinner()`。

### 4.3 🟡 CLI 模式交互增强

**问题**：CLI 模式只做批量评测，不支持交互式问答。

**建议**：增加交互式问答模式：

```bash
python main.py --mode chat
# 进入交互式问答，输入 quit 退出
```

### 4.4 🟢 回答来源标注

**问题**：回答没有标注来源页码或文件。

**建议**：在回答末尾标注引用来源：


## 5. 可靠性优化

### 5.1 🔴 PDF 解析失败静默吞异常

| 当前问题 | 优化建议 |
|---------|---------|
| `parse_pdf` 方法中 try-except 捕获所有异常后 `return []` | 区分异常类型，关键错误应向上传播 |

**现状代码**（pdf_parser.py 第 152~161 行）：

```python
def parse_pdf(self, pdf_path: str) -> List[Document]:
    try:
        chunks = self._parse_pdf_with_mineru(pdf_file)
        return chunks
    except Exception:
        logger.exception(...)
        return []  # 静默吞异常
```

**建议方案**：

```python
def parse_pdf(self, pdf_path: str) -> List[Document]:
    try:
        return self._parse_pdf_with_mineru(pdf_file)
    except MinerUError:
        # MinerU 本身不可用，尝试降级
        logger.warning("mineru unavailable, falling back to pymupdf")
        return self._parse_pdf_with_pymupdf(pdf_file)
    except FileNotFoundError:
        logger.error("pdf file not found: %s", pdf_file)
        raise  # 文件不存在应该报错
    except Exception:
        logger.exception("unexpected error parsing pdf: %s", pdf_file)
        raise  # 未知错误不应静默吞掉
```

### 5.2 🟡 LLM 调用重试退避

**问题**：当前失败后逐个尝试 `FALLBACK_MODELS`，但没有退避策略。

**建议**：使用指数退避（exponential backoff）：

```python
import time

for attempt in range(3):
    try:
        resp = self.client.chat.completions.create(...)
        return resp
    except (openai.APIError, openai.APITimeoutError) as e:
        if attempt == 2:
            raise
        time.sleep(2 ** attempt)  # 1s → 2s → 4s
```

### 5.3 🟡 添加请求级别的健康检查

**问题**：无法快速判断系统各组件是否健康（LLM、PDF解析器、BM25索引）。

**建议**：增加 `health` 端点：

```python
def health_check():
    return {
        "bm25_index": bool(self.vector_store.bm25),
        "document_count": len(self.vector_store.documents),
        "llm_available": self.llm_engine.client is not None,
        "pdf_count": len(list(Path("data").glob("*.pdf"))),
    }
```

### 5.4 🟢 日志敏感信息过滤

**问题**：`app.log` 中可能记录用户输入的问题，包含敏感信息。

**建议**：在日志配置中添加敏感信息过滤器，或记录脱敏后的内容。

## 6. 安全优化

### 6.1 🟡 API Key 泄露风险

| 风险 | 建议 |
|------|------|
| `.env` 文件未加密存储 API Key | 确保 `.gitignore` 包含 `.env` |
| `app.log` 可能记录 API 调用信息 | 日志中过滤 API Key |

### 6.2 🟢 Streamlit 端口暴露

**问题**：Streamlit 默认只绑定 localhost，但如果部署到服务器需注意。

**建议**：在 main.py 中确认 `--server.address localhost`，不绑定 0.0.0.0。

### 6.3 🟢 PDF 文件路径遍历

**问题**：`data/` 目录扫描使用 `glob("*.pdf")`，暂无路径遍历问题。但如果后续支持用户上传 PDF，需做路径安全检查。
