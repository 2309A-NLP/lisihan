## 1. 已完成的优化（vs 问答系统1）

### 1.1 🔥 混合检索架构（最大改进）

| 方面 | 问答系统1 | 问答系统2 |
|------|-----------|-----------|
| 检索方式 | 仅 BM25 | **BM25 + 向量检索 + RRF 融合** |
| 检索模式 | 固定 bm25 | 支持 hybrid / bm25 / vector 三种模式可选 |
| RRF 融合 | 无 | K=30, BM25 权重 3.0, 向量权重 1.0 |

**对应文件**：`src/retriever.py` → `HybridRetriever` 类

关键代码（retriever.py 第 305~320 行）：

```python
def _rrf_fuse(self, rankings, top_k):
    for ranking_index, ranking in enumerate(rankings):
        weight = bm25_weight if ranking_index == 0 else vector_weight
        for rank, hit in enumerate(ranking, start=1):
            fused_scores[key] = fused_scores.get(key, 0.0) + weight / (rrf_k + rank) + hit.score * 0.001
```

## 2. 仍需优化的项目

### 2.1 🔴 BM25 索引持久化（从问答系统1带来的遗留问题）

**当前状态**：每次启动或重建索引时重新解析 PDF + 构建 BM25 索引。

**分析**：虽然问答系统2可以通过 `load_parsed_multiple_pdfs()`（第 500 行）从 `_chunks.json` 加载已解析的 chunk，避免了重复的 MinerU PDF 解析，但 **BM25 索引本身仍然需要重建**（`create_vectorstore` 第 193 行），对于 2000+ chunk 的文档，分词和索引构建仍需 1~3 秒。

**建议**：

```python
def save_bm25_index(self, path: str = None):
    import pickle
    path = path or f"disk/{self.collection_name}_bm25.pkl"
    data = {
        "documents": [(sd.doc.page_content, sd.doc.metadata, sd.tokens) for sd in self.documents],
        "collection_name": self.collection_name,
    }
    with open(path, "wb") as f:
        pickle.dump(data, f)

def load_bm25_index(self, path: str = None):
    import pickle
    path = path or f"disk/{self.collection_name}_bm25.pkl"
    if not os.path.exists(path):
        return False
    with open(path, "rb") as f:
        data = pickle.load(f)
    self.documents = [_StoredDocument(Document(c, m), t) for c, m, t in data["documents"]]
    self.bm25 = BM25Okapi([sd.tokens for sd in self.documents])
    return True
```

**预期收益**：启动时间从 1~3 秒降低到 < 0.1 秒。

### 2.2 🔴 仍调用私有方法 `_extract_answer_from_context`

**当前状态**：`rag_engine.py` 第 324 行仍调用了 `self.llm_engine._extract_answer_from_context(question, context)`。

**问题**：这是 Python 私有方法（以下划线开头），跨模块调用语义上不合适。

**建议**：改为公开方法名（已在问答系统2的 `llm_engine.py` 中保留该方法，只需在 `generate_answer` 中内部调用，而非外部直接调用）。

### 2.3 🔴 `answer()` 转发方法仍存在

**当前状态**：`rag_engine.py` 第 372~373 行：

```python

    return self.ask(question, ...)
```

**建议**：合并或移除，保持调用链简单。

### 2.4 🟡 真正的 LLM 流式输出

**当前状态**：`stream_answer()` 仍然是先生成完整回答再分块输出（第 366~369 行）：

```python
def stream_answer(self, ...):
    answer = self.generate_answer(...)
    for chunk in self._chunk_text(answer):
        yield chunk
```

**app.py 第 227~230 行** 也是假流式（每 18 字符 + sleep）。

**建议**：使用 OpenAI SSE 流式 API：

```python
def stream_answer_real(self, ...):
    response = self.client.chat.completions.create(
        model=...,
        messages=...,
        stream=True,
    )
    for chunk in response:
        if chunk.choices[0].delta.content:
            yield chunk.choices[0].delta.content
```

### 2.5 🟡 `_extract_answer_from_context` 仍偏长

**当前状态**：llm_engine.py 第 191~292 行，约 100 行。

**改进幅度**：相比问答系统1（152~236 行约 84 行），虽然引入了 `_is_military_income_amount_question` 辅助方法，但整体仍然偏长。

### 2.6 🟡 中文分词的 `_tokenize` 还可优化

**当前状态**：retriever.py 第 79~90 行，使用正则 `[\\u4e00-\\u9fff]{2,}` 提取中文 + 二元分词。对于"直接和间接向国防客户的销售额合计"这类长句，二元分词会生成大量无意义片段。

**建议**：

```python
# 方式1：使用 jieba 分词
import jieba

def _tokenize(self, text: str) -> List[str]:

    for word in jieba.cut(normalized):
        if len(word) >= 2:
            tokens.append(word)
    return tokens

# 方式2：混合模式（保留现有逻辑 + jieba 扩展）
def _tokenize(self, text: str) -> List[str]:
    # 保持现有英文/数字 token 提取
    # 中文部分改用 jieba
    ...
```

## 3. 新增潜在问题

问答系统2 在引入新功能的同时，也引入了新的复杂度：

### 3.1 🟡 Milvus 服务依赖

- 启动前需要先 `docker-compose up -d` 启动 Milvus + Redis
- Milvus 首次启动拉取镜像约需 2~5 分钟
- 如果 Milvus 不可用，长期记忆和向量检索功能自动降级
- 但降级逻辑中的错误日志可能让用户困惑

### 3.2 🟡 Lazy Loading 的首次延迟

`SentenceTransformer` 模型（~300MB）在首次调用 `_embed_query` 或 `_embed` 时加载，首次问答响应可能延迟 3~5 秒。

### 3.3 🟡 BM25 关键词同步

在 `HybridRetriever` 中：
- `_query_synonyms`（retriever.py 第 43~58 行）
- `_noise_terms`（retriever.py 第 59~73 行）

在 `LLMEngine` 中：
- `_expand_keywords`（llm_engine.py 第 121~143 行）
- `_extract_keywords` 的停用词（第 102~119 行）

**问题**：同义词和噪声词在不同模块中重复定义，更新时容易遗漏。

### 3.4 🟢 PDF 解析降级路径消失

问答系统1 支持 `PDF_PARSER_BACKEND=auto|mineru|pymupdf`，但问答系统2 固定为 MinerU（第 410~411 行）：

```python
if parser_backend.lower().strip() != "mineru":
    raise ValueError("Only MinerU parsing is supported.")
```

如果 WSL MinerU 不可用，系统将完全无法解析 PDF（问答系统1 会自动降级到 PyMuPDF）。
