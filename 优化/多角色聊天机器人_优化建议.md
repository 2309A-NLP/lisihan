# 多角色聊天机器人 — 优化建议报告

> 基于对整个项目代码的审查（main.py、app/core/rag.py、app/core/vectorstore.py、
> app/core/chat_context.py、app/core/auth.py、app/services/user_service.py、
> config/config.py、config/mysql_config.py 等），整理出以下优化点。

---

## 🔴 高优先级（建议立即修复）

### 1. 安全漏洞 — 管理员硬编码账号
- **位置**：`app/services/user_service.py:185-215`
- **问题**：`admin/admin123` 硬编码在登录逻辑中，且跳过密码验证直接登录
- **风险**：任何知道此账号的人可直接获得管理员权限
- **建议**：
  - 删除硬编码逻辑，改用初始化脚本创建管理员账号
  - 强制管理员首次登录修改密码
  - 或使用环境变量配置初始管理员密码

### 2. 安全漏洞 — JWT 密钥暴露在 Git 中
- **位置**：`.env` 文件（已在 Git 仓库中）
- **问题**：`SECRET_KEY=b80a51c7db1bbab2f...` 明文提交到 Git，推送到远程即可被所有人看到
- **风险**：拿到密钥后可伪造任意用户的 JWT token
- **建议**：
  - 将 `.env` 添加到 `.gitignore`（不要提交）
  - 创建 `.env.example` 模板文件
  - 生产环境和开发环境使用不同的密钥
  - 运行 `git rm --cached .env` 从 Git 中移除

### 3. 安全漏洞 — CORS 全部开放
- **位置**：`main.py:65`
- **问题**：`allow_origins=["*"]` 允许任何域名访问 API
- **风险**：任意第三方网站可通过用户浏览器发起跨域请求
- **建议**：明确指定允许的域名列表，或在配置中控制

### 4. 安全风险 — JWT 配置暴露接口
- **位置**：`main.py:166-176`
- **问题**：`/test-jwt-config` 接口直接暴露加密算法和密钥前缀
- **建议**：生产环境删除此接口，或增加管理员鉴权

### 5. 性能问题 — 每次操作都建表
- **位置**：`app/services/user_service.py` 中 15 处调用 `Base.metadata.create_all(bind=engine)`、`app/api/chat.py` 中 `_ensure_chat_tables()`
- **问题**：每次用户注册、登录、查询都在运行时尝试创建表，浪费大量数据库连接和 I/O
- **建议**：
  - 只在应用启动时（`main.py` 的 `startup_event`）调用一次建表
  - 删除所有运行时 `create_all()` 调用

## 🟡 中优先级（建议近期优化）

### 6. 代码结构 — rag.py 过于臃肿
- **位置**：`app/core/rag.py` — **1057 行 / 52KB**
- **问题**：一个文件承担了太多职责：
  - 向量化模型管理
  - BM25 检索
  - Milvus 向量检索
  - 评分/排序逻辑
  - 查询扩展
  - LLM 调用
  - 知识库管理
- **建议**：拆分为多个模块：
  - `rag/retriever.py` — 检索逻辑
  - `rag/scorer.py` — 评分排序
  - `rag/llm.py` — LLM 调用
  - `rag/knowledge.py` — 知识库管理
  - `rag/embedding.py` — 向量化

### 7. 数据库编码问题
- **位置**：`config/mysql_config.py:16`
- **问题**：`MYSQL_CHARSET = "utf8"` — MySQL 的 `utf8` 实际是 `utf8mb3`，**不支持存储 emoji 和部分生僻字**
- **风险**：用户输入 emoji 或特殊字符会导致数据库写入失败
- **建议**：改为 `utf8mb4`，对应的排序规则用 `utf8mb4_unicode_ci`

### 8. 嵌入式向量模型路径
- **位置**：`config/config.py:87-93`
- **问题**：`EMBEDDING_MODEL` 和 `RERANK_MODEL` 使用 Windows 绝对路径：
  ```
  C:\Users\freedom\Desktop\专业\模型\bge-base-zh-v1.5
  ```
- **风险**：换一台机器就必须改代码，且路径中带中文/空格容易出错
- **建议**：
  - 改到 `.env` 中配置，不要硬编码
  - 支持相对路径
  - 提供自动下载模型的 fallback 逻辑

### 9. 部署模式问题
- **位置**：`start.bat:43`
- **问题**：`uvicorn main:app --reload --port 8080` — `--reload` 是开发模式，会额外监听文件变化
- **建议**：
  - 部署脚本去掉 `--reload`
  - 或分两个脚本：`dev.bat`（带 reload）和 `start.bat`（不带）

### 10. Fallback Token 安全性
- **位置**：`app/core/auth.py:28-46`
- **问题**：当 `python-jose` 不可用时，使用 base64 编码的 JSON 作为 token，任何人都可以解码伪造
- **建议**：
  - 将 `python-jose` 和 `passlib` 作为**必需依赖**（移到 requirements.txt 的必装列表）
  - 移除 fallback token 逻辑

### 11. 数据库迁移管理
- **问题**：使用 `Base.metadata.create_all()` 进行建表，无法追踪表结构变更，多人协作时容易冲突
- **建议**：
  - 引入 Alembic 管理数据库迁移
  - 记录每次变更的迁移脚本

## 🟢 低优先级（建议后续迭代）

### 12. 多重记忆检索超时串行等待
- **位置**：`app/core/rag.py:301-309`
- **问题**：4 路并行检索（BM25、本地向量、Milvus、Milvus关键词）中，最慢的一路（Milvus 超时 5s）会拖慢整体响应
- **建议**：
  - 使用 `as_completed` 处理结果，先到的先用
  - 或设置全局最大等待时间（如 2s），超时则跳过未返回的路

### 13. 搜索缓存缺少过期机制
- **位置**：`app/core/rag.py:294-295`
- **问题**：`query_cache` 字典不断增长，没有大小限制和过期时间
- **建议**：使用 `lru_cache` 或 Redis 缓存，设置 TTL

### 14. 并行检索超时后任务仍在运行
- **位置**：`app/core/rag.py:301-309`
- **问题**：`future.result(timeout=2)` 超时会抛出 `TimeoutError`，但后台线程仍然在运行，浪费资源
- **建议**：超时后调用 `future.cancel()`，使用 `wait()` + `FIRST_COMPLETED`

### 15. 代码冗余 — 双重编码声明
- **位置**：`app/core/chat_context.py:1-2`
- **问题**：连续两行 `# -*- coding: utf-8 -*-`，多余
- **建议**：删除重复行

### 16. BM25 索引每次都全量重建
- **位置**：`app/core/rag.py:259-274`
- **问题**：每次启动都重新分词并重建 BM25 索引
- **建议**：持久化 BM25 索引到磁盘，启动时仅增量更新

### 17. 敏感词过滤过于简单
- **位置**：`app/core/cleaner.py:77-100`
- **问题**：简单字符串替换 `replace(word, '**')`，且敏感词列表中有 `"微信"`、`"QQ"` 等正常词汇
- **风险**：正常聊天内容中提及"微信"会被自动屏蔽
- **建议**：
  - 使用正则匹配整词（不是子串）
  - 区分场景（知识库 vs 用户聊天）
  - 降低敏感词过滤的误杀率

### 18. 前端代码未模块化
- **位置**：`frontend/` 目录
- **问题**：纯静态 HTML，`index.html` 68KB、`admin.html` 54KB，JS/CSS 全部内嵌
- **建议**：
  - 拆分为组件化开发（Vue/React）
  - 引入构建工具打包

### 19. MySQL 连接使用 `mysql-connector-python` 而不是 `pymysql`
- **位置**：`requirements.txt:9`
- **问题**：`mysql-connector-python` 是 Oracle 官方驱动，但兼容性和社区支持不如 `pymysql`
- **建议**：切换到 `pymysql`，或确保 `mysql-connector-python` 版本与 MySQL 版本对齐

### 20. 日志级别和格式不统一
- **位置**：多处，`rag.py` 中混合使用 `print()` 和 `logger.info()`
- **问题**：部分日志用 `print` 输出到 stdout，部分用 `logger`，格式和级别不一致
- **建议**：统一使用 `logger`，禁用 `print()`，生产环境可配置 JSON 格式日志便于采集

### 21. 缺少容器化部署方案
- **问题**：项目依赖 MySQL、Redis、Milvus 三个外部服务，手动配置繁琐
- **建议**：
  - 提供 `docker-compose.yml` 一键启动所有依赖
  - 应用本身也打包为 Docker 镜像
