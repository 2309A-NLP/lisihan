## 1. 端口冲突解决

### 背景

Dify plugin-daemon 默认占用以下端口：

- **5002** — HTTP 管理 API
- **5003** — gnet TCP 通信

Windows 宿主上已有其他服务占用相同端口：

- **基金问答后端** — 原端口 5002
- **招股书问答后端** — 原端口 5003

导致插件守护进程与业务服务端口冲突，容器无法正常启动或服务互相干扰。

### 问题描述

| 服务 | 原端口 | 冲突服务 |
|------|--------|----------|
| 基金问答后端 | 5002 | Dify plugin-daemon HTTP |
| 招股书问答后端 | 5003 | Dify plugin-daemon gnet TCP |

冲突表现为：基金/招股书 API 调用超时、响应错误，或 Dify 插件管理页面无法加载。

### 解决方案

对所有涉及的服务端口进行统一迁移：

| 服务 | 原端口 | 新端口 |
|------|--------|--------|
| 基金问答后端 | 5002 | **5004** |
| 招股书问答后端 | 5003 | **5005** |

同步修改涉及以下文件与配置：

1. **app.py** — 后端服务启动端口配置
2. **agent.py** — `TOOL_API_ENDPOINTS` 中定义的 API 端点 URL
3. **web_app.py** — `TOOL_APIS` 中定义的工具 API 地址
4. **launcher.py** — 服务启动与健康检查的端口号
5. **Dify 工作流 HTTP 节点 URL** — 所有引用后端服务的节点

Dify 工作流中对应的 URL 变更：

- `http://host.docker.internal:5002/...` → `http://host.docker.internal:5004/...`
- `http://host.docker.internal:5003/...` → `http://host.docker.internal:5005/...`

### 效果

- ✅ 基金问答服务与 Dify plugin-daemon 端口不再冲突
- ✅ 招股书问答服务与 Dify plugin-daemon 端口不再冲突
- ✅ 所有 Dify 工作流 HTTP 节点可正确访问后端服务
- ✅ 容器化部署与 Windows 宿主服务可共存运行

## 2. LLM 意图分类提示词平衡

### 背景

原始 LLM 路由分类提示词中，五个示例数据的分布严重不平衡：

| 路由 | 示例数量 |
|------|----------|
| 记账本 | 3 个 |
| 日程提醒 | 1 个 |
| 文生图 | 1 个 |

这种倾斜导致模型在意图识别时**默认倾向输出"记账本"**，即使用户输入的是基金查询或招股书查询，也被错误路由到记账本流程。

### 问题描述

- 用户输入"基金 007202 净值" → 模型输出"记账本"
- 用户输入"查询招股书" → 模型输出"记账本"
- 路由准确率低，用户体验差

### 解决方案

#### 2.1 示例分布平衡

每个路由至少包含 **2~3 个示例**，确保模型在各路由间无统计偏好。

#### 2.2 基金路由示例扩充

新增 **8 个触发词/短语**：

| 触发词 | 说明 |
|--------|------|
| 基金 | 泛基金查询 |
| 基金代码 | 如"007202" |
| 净值 | 基金净值查询 |
| 收益率 | 基金收益率查询 |
| 行情 | 基金/股票行情 |
| 股票 | 股票行情查询 |
| 涨跌幅 | 涨跌幅度查询 |
| 收盘价 | 收盘价查询 |

#### 2.3 招股书路由示例扩充

新增 **9 个触发词/短语**：

| 触发词 | 说明 |
|--------|------|
| 招股书 | 招股说明书查询 |
| 招股说明书 | 全称匹配 |
| IPO | 首次公开募股 |
| 发起人 | 发起人信息 |
| 法人 | 法人信息 |
| 股东 | 股东信息 |
| 股权 | 股权结构 |
| 上市 | 上市信息 |
| 发行人 / 注册资本 | 发行人与注册资本查询 |

#### 2.4 硬性规则注入

在提示词中加入明确的规则约束，例如：

> **规则**：如果用户输入包含"花了"或"支出"等记账关键词，路由到"记账本"。
> **示例**："花了35元买奶茶" → 记账本

#### 2.5 路由优先级

当多个路由条件同时满足时，按以下优先级执行：

```
文生图 > 基金 > 招股书 > 记账本 > 日程提醒
```

### 效果

- ✅ 路由分类准确率显著提升
- ✅ 基金查询正确路由到基金流程
- ✅ 招股书查询正确路由到招股书流程
- ✅ 记账本不再成为默认输出
- ✅ 硬性规则保证特定输入无歧义路由

## 3. 条件分支关键词匹配优化

### 背景

用户输入"查询招股书"，但 Dify 工作流中的条件分支节点仅配置了`equals`精确匹配"股票"，导致匹配失败，路由错误。

### 问题描述

- 条件分支使用 `equals`（精确匹配），但用户输入为自然语言，词形多样
- 招股书路由仅配置了"股票"一个关键词
- 用户说"招股书"时匹配不到任何条件，进入默认流程
- 同义词缺失导致匹配盲区

### 解决方案

#### 3.1 匹配模式变更

将条件分支的匹配模式从 `equals`（精确匹配）改为 `contains`（包含匹配）：

```
匹配方式: equals → contains
```

这样用户输入"我要查招股书"中只要包含"招股书"即可匹配。

#### 3.2 招股书路由条件扩充

在招股书路由的条件分支中，使用 `logical_operator=or` 组合多个条件：

```yaml
conditions:
  - variable: "#sys.query#"
    operation: contains
    value: "股票"
  - variable: "#sys.query#"
    operation: contains
    value: "招股书"
logical_operator: or
```

#### 3.3 每个条件分支的同义词扩充

对所有路由的条件分支进行同义词扩充：

| 路由 | 关键词/同义词 |
|------|---------------|
| 基金 | 基金, 净值, 收益率, 行情, 股票, 涨跌幅, 收盘价 |
| 招股书 | 招股书, 招股说明书, IPO, 上市, 发行人, 股东, 股权 |
| 记账本 | 记账, 花了, 支出, 收入, 流水, 账单 |
| 日程 | 日程, 提醒, 会议, 待办, 通知 |
| 文生图 | 生成图片, 画图, 绘图, 文生图, AI图片 |

### 效果

- ✅ 用户说"招股书"可正确匹配招股书路由
- ✅ `contains` 匹配容忍更多自然语言变体
- ✅ `or` 逻辑确保任一关键词触发即可
- ✅ 同义词覆盖减少漏匹配

## 4. HTTP 节点 Body 参数统一

### 背景

Dify 工作流中的 HTTP 请求节点向基金/招股书后端发送数据时，某些节点的 Body 参数名使用了 `"message"` 而非 `"query"`，导致后端接口无法正确解析传入的查询内容。

### 问题描述

- 部分 HTTP 节点 Body 结构：`{"message": "{{#sys.query#}}"}`
- 后端接口期待的 Body 结构：`{"query": "用户输入内容"}`
- 参数名不匹配 → 后端收到的 `query` 字段为 `null` → 返回空结果或错误

### 解决方案

#### 4.1 Body 参数名统一

将所有 HTTP 节点的 Body 参数统一为：

```json
{
  "query": "{{#sys.query#}}"
}
```

使用 Dify 系统变量 `sys.query` 确保始终获取用户的原始输入文本。

#### 4.2 涉及节点

对所有调用基金/招股书后端的 HTTP 节点逐一检查并修正 Body 结构：

| 节点 | 修正前 | 修正后 |
|------|--------|--------|
| 调用基金 API | `{"message": "{{#sys.query#}}"}` | `{"query": "{{#sys.query#}}"}` |
| 调用招股书 API | `{"message": "{{#sys.query#}}"}` | `{"query": "{{#sys.query#}}"}` |

### 效果

- ✅ 后端接口正确收到 `query` 参数
- ✅ 基金查询返回正常结果
- ✅ 招股书查询返回正常结果
- ✅ `sys.query` 确保获取原始用户输入，避免变量传递丢失

## 5. 后处理 LLM 节点 Prompt 修正

### 背景

基金和招股书的 HTTP 请求节点之后，分别接有后处理 LLM 节点（LLM 5 和 LLM 6），用于格式化输出。但这两个节点的 System Prompt 内容错误——**误写为"用户查询了记账数据"**，并要求输出"总收入、总支出、预算剩余"等记账格式。

### 问题描述

- **LLM 5**（基金后处理）：prompt 要求按记账格式输出
- **LLM 6**（招股书后处理）：prompt 同样要求按记账格式输出
- 基金 API 返回的净值数据被强行套入"总收入/总支出"框架
- 招股书 API 返回的股权结构数据同样被套入记账框架
- 输出内容与用户预期完全不符

### 解决方案

#### 5.1 LLM 5 — 基金后处理 Prompt

修正前（错误）：

```text
你是一个智能助手。用户查询了记账数据，请根据以下数据回答。
输出应包括：总收入、总支出、预算剩余、交易明细...
```

修正后（正确）：

```text
你是一个基金查询助手。用户查询了基金相关信息，请根据以下数据回答。
输出应包括：基金名称、基金代码、最新净值、日涨跌幅、累计净值、更新时间。
回答要简洁清晰，使用友好的中文。
```

#### 5.2 LLM 6 — 招股书后处理 Prompt

修正前（错误）：

```text
你是一个智能助手。用户查询了记账数据，请根据以下数据回答。
输出应包括：总收入、总支出、预算剩余...
```

修正后（正确）：

```text
你是一个招股书查询助手。用户查询了招股说明书信息，请根据以下数据回答。
输出应包括：股票名称、发行人、注册资本、主营业务、发行日期、相关股东信息。
回答要简洁清晰，使用友好的中文。
```

#### 5.3 原则

每个后处理 LLM 节点都有**独立的、匹配其数据源的 prompt**，不得复用或复制粘贴其他路由的 prompt。

### 效果

- ✅ LLM 5 正确输出基金净值信息
- ✅ LLM 6 正确输出招股书信息
- ✅ 不再出现基金数据套记账模板的格式混乱
- ✅ 输出内容与用户查询意图一致

## 6. Dify API 草稿保存 Hash 校验

### 背景

通过 Dify REST API 修改工作流草稿（draft）时，如果不传 `hash` 字段，Dify 会返回以下错误：

```json
{
  "code": "draft_workflow_not_sync",
  "message": "Draft workflow not synced",
  "status": 400
}
```

### 问题描述

- 每次通过 API 更新草稿后，`hash` 值会发生变化
- 后续修改必须携带最新的 `hash`，否则请求被拒绝
- 手动追踪 `hash` 容易遗漏，导致自动化脚本中断

### 解决方案

采用链式操作流程：

```
step 1: GET  /apps/{app_id}/workflows/draft
        → 获取当前草稿的 hash 字段

step 2: POST /apps/{app_id}/workflows/draft
        Body: { ..., "hash": "<从step1获取的hash>" }
        → 修改成功，返回新的 hash

step 3: 如需再次修改，使用 step 2 返回的 hash
```

每次 POST 前，先 GET 获取最新 `hash`，再携带该 `hash` 发起修改请求。获取下一个 `hash` 作为下一次修改的前置条件。

### 效果

- ✅ 所有草稿更新请求均携带正确 `hash`
- ✅ 不再出现 `draft_workflow_not_sync` 错误
- ✅ 自动化脚本可稳定执行多轮工作流修改
- ✅ hash 链式获取保证每次修改基于最新版本

## 7. Docker 容器绑定挂载路径修复

### 背景

项目最初部署在 Windows 桌面上，后来将 Dify 目录从桌面迁移到 `C:\Users\freedom\Dify\`。但 `docker-compose.yml` 中的绑定挂载路径仍指向旧位置（桌面路径），导致容器启动失败。

### 问题描述

- `docker-compose.yml` 中的 `volumes` 配置使用了相对路径或旧绝对路径
- `plugin_base.py` 等关键文件挂载指向不存在的旧路径
- 尝试启动容器时报错：挂载源路径不存在
- Docker 容器无法正常启动，影响整个应用可用性

### 解决方案

#### 7.1 清理损坏容器

```bash
docker rm -f dify-api
```

#### 7.2 从新路径重新创建

```bash
cd C:\Users\freedom\Dify\
docker compose -f docker-compose.yml up -d --no-deps api
```

参数说明：

- `-f` 指定从新路径加载 `docker-compose.yml`
- `--no-deps` 仅启动指定服务，不重建依赖服务
- `up -d` 后台启动容器

#### 7.3 路径对齐

确保 `docker-compose.yml` 中所有 `volumes` 绑定路径指向当前项目目录：

```yaml
volumes:
  - ./plugin_base.py:/app/plugin_base.py
  - ./data:/app/data
  # ... 其他挂载项
```

### 效果

- ✅ 损坏的容器已删除
- ✅ 从新路径重新创建容器成功
- ✅ 绑定挂载路径正确指向 `C:\Users\freedom\Dify\`
- ✅ `dify-api` 服务正常运行
- ✅ 所有挂载文件可正常读写

## 8. 管理员密码修复

### 背景

Dify 部署完成后，使用默认密码 `password123` 无法登录管理员账户，提示密码错误。

### 问题描述

- 默认密码 `password123` 不匹配数据库中存储的密码哈希
- 无法通过常规登录界面进入管理员后台
- 通过数据库直接重置密码需要生成与 Dify 认证机制兼容的密码哈希

### 解决方案

#### 8.1 密码哈希生成

Dify 使用 **PBKDF2-HMAC-SHA256** 算法存储密码。通过 Python 脚本生成新密码哈希：

```python
import hashlib
import base64

password = "admin123"
# Dify 的密码哈希生成方式（PBKDF2-HMAC-SHA256）
salt = os.urandom(16)
dk = hashlib.pbkdf2_hmac('sha256', password.encode(), salt, 100000)
hash_value = base64.b64encode(salt + dk).decode()
```

实际生成的哈希值已通过 Dify 源码中 `extensions/ext_login.py` 或 `models/account.py` 中的认证函数验证。

#### 8.2 数据库更新

连接 PostgreSQL 数据库，更新 `accounts` 表的密码字段：

```sql
UPDATE accounts
SET password = '<新生成的PBKDF2哈希值>'
WHERE email = 'admin@example.com' OR name = 'admin';
```

#### 8.3 新密码

| 项目 | 值 |
|------|-----|
| 用户名 | admin |
| 新密码 | **admin123** |

### 效果

- ✅ 管理员账户恢复可用
- ✅ 使用 `admin123` 可成功登录 Dify 管理后台
- ✅ 密码存储与 Dify 的 PBKDF2-HMAC-SHA256 认证机制兼容
- ✅ 无需重建数据库或重新部署

## 9. 系统整体架构与用户偏好

### 背景

SmartAgent Pro 最终的 Agent 行为和输出格式需要符合明确的用户偏好约束，确保用户体验流畅、结果准确。

### 用户偏好配置

#### 9.1 工具调用策略（单工具调用）

**要求**：Agent 必须只调用一个工具，不准试遍所有工具返回一堆结果。

**配置方式**：

- Agent 系统提示词中加入约束：
  ```
  关键约束：
  - 你一次只能调用一个工具
  - 不要为了"保险"而依次调用多个工具
  - 分析用户的意图，精确选择一个最合适的工具
  - 如果选错了，等待用户反馈再修正
  ```

#### 9.2 输出格式（干净简洁）

**要求**：结果输出要干净，不要前缀包装，例如不要加`"根据查询结果..."`等多余描述。

**配置方式**：

- Agent 提示词中加入：
  ```
  输出约束：
  - 直接输出查询结果，不要添加"根据查询结果"、"好的"、"这是您要的信息"等前缀
  - 不要使用Markdown代码块包装
  - 保持简洁、结构化、易读
  ```

#### 9.3 文生图调用限制

**要求**：数据查询后不准自动调用文生图，除非用户明确要求画图。

**配置方式**：

- 在工具调用决策逻辑中加入条件判断：
  ```
  只有在以下情况才调用文生图工具：
  - 用户输入中包含"画"、"生成图片"、"绘图"等明确关键词
  - 用户直接要求"生成一张图片"
  以下情况禁止调用文生图：
  - 查询基金净值后 → 不画图
  - 查询招股书后 → 不画图
  - 查询记账数据后 → 不画图
  ```

#### 9.4 错误消息处理（中文友好）

**要求**：错误消息必须用中文且友好，不准显示 Python 原始异常堆栈。

**配置方式**：

- Agent 提示词中加入：
  ```
  错误处理规则：
  - 所有错误消息必须用中文输出
  - 禁止返回 Python 异常堆栈（Traceback）
  - 错误消息示例：
    - "抱歉，查询基金信息时遇到问题，请稍后重试。"
    - "暂时无法获取招股书数据，请检查输入是否正确。"
    - "网络连接异常，请确认服务状态。"
  ```

### 效果

- ✅ Agent 每次只调用一个工具，不产生冗余结果
- ✅ 输出简洁，无多余前缀包装
- ✅ 数据查询后不会自动触发文生图
- ✅ 错误信息友好中文显示，无原始异常堆栈泄露
