### 6.3 构建工作流图

工作流采用 **Star — LLM — Condition — Route — LLMs — Reply** 的链式架构。

#### 6.3.1 节点清单

| 节点名称               | 类型       | 说明                                                       |
|------------------------|------------|------------------------------------------------------------|
| **Start**              | Start      | 工作流入口，接收用户输入                                   |
| **LLM（意图分类器）**  | LLM        | 分析用户意图，输出格式要求为 `"tool 工具名称"`               |
| **条件分支1**          | Condition  | 判断 LLM 输出是否包含 "tool" 关键字，是则进入路由，否则直接回复 |
| **条件分支2（路由）**  | Condition  | 根据工具名称路由到对应的后端服务                             |
| **LLM2（记账本）**     | LLM        | 处理记账本查询结果并生成自然语言回复                         |
| **LLM3（日程提醒）**   | LLM        | 处理日程查询结果并生成自然语言回复                           |
| **LLM4（文生图）**     | LLM        | 处理图片生成结果并生成回复                                   |
| **LLM5（基金）**       | LLM        | 处理基金查询结果并生成自然语言回复                           |
| **LLM6（招股书）**     | LLM        | 处理招股书查询结果并生成自然语言回复                         |

#### 6.3.2 边连接关系

```
Start → LLM（意图分类器）
LLM（意图分类器） → 条件分支1
条件分支1（含 "tool"） → 条件分支2（路由）
条件分支1（不含 "tool"） → 直接回复用户
条件分支2 →
  ├─ "记账" → HTTP(记账本) → LLM2 → 回复
  ├─ "日程" → HTTP(日程提醒) → LLM3 → 回复
  ├─ "生图" → HTTP(文生图) → LLM4 → 回复
  ├─ "基金" → HTTP(基金) → LLM5 → 回复
  └─ "招股" → HTTP(招股书) → LLM6 → 回复
```

#### 6.3.3 意图分类器 Prompt（示例）

```
你是一个智能助手意图分类器。请分析用户输入，判断其意图并输出工具名称。

输出格式（仅输出以下格式，不要有多余内容）：
- 如果用户想记账或查账，输出：tool 记账本
- 如果用户想查看日程或提醒，输出：tool 日程提醒
- 如果用户想生成图片，输出：tool 文生图
- 如果用户想查询基金信息，输出：tool 基金
- 如果用户想查询招股书信息，输出：tool 招股书
- 如果以上都不匹配，直接回复用户的问题。
```

### 6.4 配置 HTTP 节点连接 Windows 宿主服务

所有后端服务运行在 **Windows 宿主操作系统** 上，Dify 容器通过 `host.docker.internal` 访问宿主机端口。

Dify 工作流中的 HTTP 节点配置示例：

| 工具名称   | HTTP 节点 URL                                         | 方法   | 请求头                      |
|------------|-------------------------------------------------------|--------|-----------------------------|
| 记账本     | `http://host.docker.internal:8081/api/chat`           | POST   | `Content-Type: application/json` |
| 日程提醒   | `http://host.docker.internal:5000/chat`               | POST   | `Content-Type: application/json` |
| 文生图     | `http://host.docker.internal:7860/generate`           | POST   | `Content-Type: application/json` |
| 基金       | `http://host.docker.internal:5004/ask`                | POST   | `Content-Type: application/json` |
| 招股书     | `http://host.docker.internal:5005/ask`                | POST   | `Content-Type: application/json` |

> **注意**：`host.docker.internal` 是 Docker Desktop for Windows 提供的特殊 DNS 名称，自动解析到 Windows 宿主机。仅在 WSL2 + Docker Desktop 环境中有效。若使用纯 Linux Docker，需替换为宿主机实际 IP。

## 9. 注意事项

### 9.1 端口冲突排查

- Dify 默认占用端口：**3000**（Web）、**5001**（API）、**5002**（Plugin HTTP）、**5003**（Plugin gRPC）。
- 若宿主机已有其他服务占用这些端口，需在 `docker-compose.yml` 中修改端口映射。
- 后端服务端口（8081、5000、7860、5004、5005）同样需确保未被占用。
- 检查端口占用命令（Windows PowerShell）：
  ```powershell
  netstat -ano | findstr ":3000"
  netstat -ano | findstr ":5001"
  ```

### 9.2 容器绑定挂载路径问题

- WSL2 中 Docker 容器的挂载路径使用 Linux 路径格式。
- 若需挂载 Windows 目录到容器，使用 `/mnt/c/...` 路径。
- 示例（在 docker-compose.yml 中）：
  ```yaml
  volumes:
    - /mnt/c/Users/freedom/Dify/data:/app/data
  ```
- 避免挂载包含中文或空格的路径，可能会导致兼容性问题。

### 9.3 Dify API Hash 验证

- Dify 某些版本在调用 API 时需要对请求参数进行 Hash 验证（如 `message_hash`）。
- 若遇到 API 调用失败并返回 hash 相关错误，在请求参数中添加 `message_hash` 字段。
- Hash 算法为 `SHA256`，计算方式：
  ```python
  import hashlib
  message_hash = hashlib.sha256(
      f"{app_id}{message}{timestamp}".encode()
  ).hexdigest()
  ```
- 使用 Dify 官方 SDK 时，SDK 会自动处理 hash 验证，建议优先使用 SDK。

### 9.4 其他注意事项

- **防火墙设置**：确保 Windows 防火墙未阻止 Docker 容器与宿主机之间的通信（`host.docker.internal` 流量）。
- **资源分配**：WSL2 默认内存限制为宿主机的 50%，可在 WSL 配置文件 `%USERPROFILE%\.wslconfig` 中调整：
  ```ini
  [wsl2]
  memory=8GB
  processors=4
  ```
- **日志查看**：Dify 容器日志查看命令：
  ```bash
  docker compose logs -f web
  docker compose logs -f api
  ```
- **备份**：定期备份 PostgreSQL 数据库和 `docker-compose.yml` 配置文件。
- **升级 Dify**：升级前务必备份数据库，然后拉取最新镜像并重启：
  ```bash
  docker compose down
  docker compose pull
  docker compose up -d
  ```
